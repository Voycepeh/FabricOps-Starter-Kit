# FabricOps Visual Design

Read `AGENTS.md` and `design/brand.json` first. Treat `design/brand.json` as the only canonical palette/typography source. `docs/stylesheets/brand-tokens.css` is generated by `python scripts/sync_brand_tokens.py`; never hand-edit the generated file.

## Mandatory external diagram skill

For ANY new/changed diagram, architecture, flow, workflow, data/processing illustration, or SVG, **read and apply** [Diagram Design](https://github.com/cathrynlavery/diagram-design) before drawing. Follow its `SKILL.md`, selected semantic-pattern reference, specific diagram-type reference, connector/typography/spacing rules and QA guidance. If its default skin differs from FabricOps, use the repository's `design/brand.json` as the customized FabricOps brand profile. Do not fall back to generic rectangles and prose. Design diagrams to illustrate operations with icons, representative data or meaningful structure. Choose SVG for editable schematics, PNG for actual screenshots. Do not fake UI captures or charts.

## Brand and typography

* Brand gradient: blue `#2563EB` to purple `#7C3AED`, reserved for website hero/header and selective focal accents. Never use a gradient as running text or fill every box.
* Blue denotes Engineering, purple Governance. Retain green/amber/red for meaningful success/warning/danger ONLY, not decorative pipeline stages.
* White canvas, restrained pale surfaces, dark ink and thin borders. No fake/unapproved logo, synthetic watermark or decorative 'FabricOps' icon.
* Website and diagrams: Segoe UI with Arial fallback. Code/API labels: Cascadia Code with Consolas fallback. Avoid bundling font files or relying on network fonts.
* One memorable focal point per visual. No 'cards everywhere', rainbow stage coloring, irrelevant icons, large callout strip, duplicate title or unnecessary glossary copy. Prefer one compact diagram per section.
* Use real, precise function names like `orchestrate_read()`, `orchestrate_write()`; lowercase parameter and mode values must be exact.
* Use short labels; move rationale and exception detail into prose. Never shrink critical text to unreadable sizes to fit a diagram.

## Source-of-truth review before art

1. Identify the exact page, audience, specific question and smallest visual needed. A comparison table may be more effective than a diagram.
2. Trace every arrow/step/callable/metadata table to current `src/fabricops_kit/`, `src/fabricops_kit/config/metadata_schemas.py`, the public exports and generated API reference, plus the Glossary. Distinguish public vs internal functions and Live vs Preview/gated behaviors. Never invent sample output as real results.
3. Sketch the semantic layout using the external Diagram Design skill. Respect the density limit and flow direction. For platform-specific icons use official licensed assets or neutral system icons, not invented branding.
4. Build SVG with readable text, coherent scale, intentional whitespace, orthogonal connectors, meaningful shapes and properly routed arrows. Prefer SVG source that is maintainable in Git. Author an accessible `<title>` or `aria-label`.
5. Render and inspect the actual SVG at page width and narrow width. Check clipping, collisions, alignment, arrows, font substitution, text contrast, and absence of unauthorized logos. Never claim visual QA without rendering.
6. Run `python scripts/sync_brand_tokens.py --check` and `python scripts/check_svg_text_bounds.py`. Fix every overflow warning before PR review. The checker uses conservative font metrics, so also render at 100% and narrow widths to catch browser-dependent overflow and arrow/text collisions. The SVG is not approved until **no text crosses its containing panel**. Run the site build and focused tests where applicable. Document explicit limitations and unresolved acceptance gates.

## Scope

Applies to documentation website, homepage, Engineering, Governance, promotion, marketing illustrations, infographics, screenshots, release graphics, notebook/widget visuals and future slide assets. Existing independent notebook widget tokens may keep the native Segoe UI sizing and separate functional semantics, but all newly created UI should reference the shared brand roles rather than invent new colors. Do not mass-rewrite archived/release snapshots or historical media unless requested.

Use `.agents/skills/fabricops-docs-maintenance/SKILL.md` for documentation structure and `.agents/skills/fabricops-widget-ui/SKILL.md` for ipywidget runtime constraints; this skill owns the common visual standard.
